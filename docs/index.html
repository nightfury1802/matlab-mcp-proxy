MATLAB MCP Compression Proxy

A lightweight stdio proxy that sits between Claude Code and the MATLAB MCP server, intercepting tool responses and compressing them before they reach the LLM context window — reducing token consumption without changing any tool semantics.

Why it exists

MATLAB MCP server responses are verbose by design — they include rich diagnostic output, full warning traces, aligned whos tables, long progress logs, and structured build output. This verbosity is useful when reading in a terminal but is expensive when consumed by an LLM.

The proxy applies 13 targeted compression rules to MATLAB tool responses. Each rule is reversible in principle (no information loss that Claude would act on), lossless for error messages, and always preserves the first and last values of numeric sequences so Claude can still reason about simulation results.

What it is not

  • Not a summarizer — it does not use an LLM to paraphrase output.
  • Not a cache — every call goes through to MATLAB.
  • Not lossy for errors — R11 strips boilerplate text, never the error message itself.
  • Not required — --bypass disables all compression for full raw output.

48% average reduction measured across the 8 test scenarios in the test suite, covering whos output, build logs, DOE progress, test runner tables, stack traces, struct display, repeated warnings, and algebraic loop reports.

Architecture

Two proxy processes wrap the two MCP servers. Both share the same MATLAB session. The proxy is a pure pass-through on requests; on responses it applies 14 compression rules before returning to Claude.

Claude Code  (~/.claude.json)
│
├─── matlab proxy (python3 proxy.py)
│         │  Content-Length framing (LSP-style JSON-RPC)
│         ▼
│    matlab-mcp-core-server --initialize-matlab-on-startup=true
│         │  starts MATLAB eagerly at Claude launch (~15-20s)
│         ▼
│    ┌─────────────────────────────────────────────┐
│    │             MATLAB R2025a                    │◄──── shared session
│    │  evaluate_matlab_code / run_matlab_file      │      connector.securePort
│    └─────────────────────────────────────────────┘
│         ▲
│    matlab-mcp-core-server --matlab-session-mode=existing
│         │  polls for session, attaches within 30s window
│         │  Content-Length framing
└─── simulink proxy (python3 proxy.py)
          + --extension-file=tools/tools.json
            (model_edit / model_overview / model_read / model_test)

RESPONSE path (both proxies):
  upstream → proxy → compress(content[].text) → Claude
  R01 deduplicate repeated warnings    [~59%]
  R02 collapse deep stack traces       [~40%]
  R03 compact whos tables              [~74%]
  R04 truncate large arrays            [~85%]
  R05 shorten Simulink block paths
  R06 compress block lists             [~63%]
  R07 collapse ### build output        [~56%]
  R08 elide progress lines             [~79%]
  R09 compact test results             [~62%]
  R10 inline struct fields             [~32%]
  R11 strip error boilerplate          [always]
  R12 dedup Caused-By                  [~58%]
  R13 compact init-cond lists
  R14 shorten model_read block paths   [~36%]
  overhead: 0.065ms median / 2.2ms worst-case

REQUEST path (both proxies):
  Claude → proxy → upstream UNCHANGED (never compressed)

Wire format: Content-Length framing

matlab-mcp-core-server uses LSP-style Content-Length framing, not newline-delimited JSON. The proxy's _read_message() auto-detects this: if the first line starts with Content-Length:, it drains all header lines then reads exactly N bytes. Otherwise it treats the line as newline-delimited JSON. Both formats are supported transparently.

Session sharing

The matlab server (new mode) writes connector.securePort to a temp directory when MATLAB starts. The simulink server (existing mode) reads this file and connects to that port. Both servers then use the same MATLAB Connector HTTP API — same workspace, same loaded models, same path.

    install.sh patches ~/Library/Application Support/Claude/claude_desktop_config.json to route the matlab MCP entry through the proxy. It saves a backup as claude_desktop_config.json.bak.

  5. Restart Claude Desktop 
    osascript -e 'quit app "Claude"'
open -a Claude
  6. Verify the proxy is active

    In Claude, run any MATLAB command. Check that repeated-warning deduplication is working:

    % In Claude: ask MATLAB to run a script that emits repeated warnings.

Rules Reference

All 13 rules are applied in order R01 → R13 on every tool response text. Rules are independent — each operates on the output of the previous rule.

R01 Deduplicate repeated warnings ~59% reduction

When the same warning line (including its stack trace) appears more than once in sequence, collapse all occurrences into a single instance annotated with a repeat count [×N].

Before
Warning: Matrix is singular to working precision.
> In solve (line 10)
Warning: Matrix is singular to working precision.
> In solve (line 10)
Warning: Matrix is singular to working precision.
> In solve (line 10)
Warning: Matrix is singular to working precision.
> In solve (line 10)
After
Warning: Matrix is singular to working precision.
> In solve (line 10)  [×4]
R02 Collapse deep stack traces ~40% reduction

When a stack trace contains more than 5 frames, keeps the first 3 and last 1 frame and replaces the middle with [... N frames ...]. The outermost call site and the innermost origin are always preserved.

Before
Error in myFunc (line 42)
Error in callA (line 15)
Error in callB (line 88)
Error in callC (line 201)
Error in callD (line 55)
Error in callE (line 7)
Error in runSim (line 3)
After
Error in myFunc (line 42)
Error in callA (line 15)
Error in callB (line 88)
[... 3 frames ...]
Error in runSim (line 3)
R03 Compact whos tables ~74% reduction

Replaces the full column-aligned whos table (Name / Size / Bytes / Class / Attributes) with a single compact line listing each variable as name[size,class]. Attribute flags (global, persistent, complex) are dropped.

Before
  Name        Size            Bytes  Class     Attributes

  Flux_dq     2x1000         16000  double
  Id          1x1                8  double
  Iq          1x1                8  double
  tout        1000x1          8000  double
  omega       1x1                8  double
  torque      1000x1          8000  double

26 lines, aligned whitespace
After
whos: Flux_dq[2x1000,dbl]  Id[1x1,dbl]  Iq[1x1,dbl]  tout[1000x1,dbl]  omega[1x1,dbl]  torque[1000x1,dbl]
R04 Truncate large numeric arrays ~85% reduction

When MATLAB echoes a numeric array with more than 20 rows in column-vector format, replaces the full listing with a one-line summary showing size, first value, and last value. This is the highest-impact rule for simulation output.

Before
torque =

         0
    1.2300
    2.4600
    3.6900
    ...
  107.6300

(977 more rows, each on its own line)
After
torque = [1000x1: first=0, last=107.6300]
R05 Shorten Simulink block paths variable

Long Simulink block paths such as myModel/Subsystem1/ControlLayer/FOC/dAxis/PIController are shortened by keeping only the model root and the last two path segments: myModel/.../PIController. Applied wherever a /-delimited path of 4 or more segments appears in the text.

Before
Block path: test_PMSM_FEM_foc/DriveUnit/
  ControlLayer/FOC/dAxis/PIController
After
Block path: test_PMSM_FEM_foc/.../PIController
R06 Compress algebraic loop block lists ~63% reduction

Algebraic loop error messages list every block in the loop. When the list exceeds 4 blocks, the middle blocks are collapsed to a count. The first two and last block are always shown so the loop topology is preserved.

Before
Algebraic loop involving the following blocks:
  'myModel/Gain1'
  'myModel/Sum1'
  'myModel/Transfer Fcn'
  'myModel/Lookup Table'
  'myModel/Product'
  'myModel/Unit Delay'
  'myModel/Gain2'
After
Algebraic loop involving the following blocks:
  'myModel/Gain1'
  'myModel/Sum1'
  [... 4 blocks ...]
  'myModel/Gain2'
R07 Collapse ### build output ~56% reduction

Simulink build logs emit many ### Starting model build... / ### Successful completion... lines. R07 keeps only the completion lines and folds them into a single summary line listing what was built.

Before

### Generating code and artifacts to 'Model' folder structure ...
### Generating code into build folder: /tmp/PMSM_Motor_ert_rtw
### Invoking Target Language Compiler (TLC) ...
### Successful completion of build procedure for model: PMSM_Motor
### Starting model build procedure for model: FOC_Controller
### Successful completion of build procedure for model: FOC_Controller
### Starting model build procedure for model: ThermalModel
### Successful completion of build procedure for model: ThermalModel
### Starting model build procedure for model: test_PMSM_FEM_foc
### Successful completion of build procedure for model: test_PMSM_FEM_foc
After
### Built: PMSM_Motor, FOC_Controller, ThermalModel, test_PMSM_FEM_foc
R08 Elide repeated progress lines ~79% reduction

DOE or batch-simulation scripts often print one progress line per point (e.g. DOE point 3/55: Id=-100, Iq=200). When more than 4 such lines match a common prefix pattern, keeps the first 2 and last 2, eliding the middle with a count.

Before

DOE point 2/21: speed=1000, torque=100
DOE point 3/21: speed=2000, torque=50
...
DOE point 19/21: speed=6000, torque=100
DOE point 20/21: speed=7000, torque=50
DOE point 21/21: speed=7000, torque=100

(21 lines total)
After
DOE point 1/21: speed=1000, torque=50
DOE point 2/21: speed=1000, torque=100
... [17 lines omitted]
DOE point 20/21: speed=7000, torque=50
DOE point 21/21: speed=7000, torque=100

MATLAB Test Framework output includes headers, separator lines, dot progress indicators, and a full results table. R09 extracts the pass/fail summary and the failure messages, discarding all decorative formatting.

FAIL (1): test_gamma
  Expected 107, got 88
R10 Inline struct field display ~32% reduction

MATLAB prints struct fields in a block format with blank lines between fields. R10 collapses this into a one-line-per-field format, removing blank lines and aligning with spaces rather than newlines.

Before
motor =

  struct with fields:

    Ld: 2.1000e-04
    Lq: 3.8000e-04
    Rs: 0.0420
    poles: 8
    psi_pm: 0.1230
After
motor: Ld=2.1000e-04  Lq=3.8000e-04  Rs=0.0420  poles=8  psi_pm=0.1230
R11 Strip "An error occurred" boilerplate always active

MATLAB wraps every error in a generic header: An error occurred during the execution of.... This header adds no diagnostic value beyond what the actual error message contains. R11 strips the wrapper and returns only the error message body.

Before
An error occurred during the execution of the MATLAB code.
Error message: Undefined function 'foc_step' for input
arguments of type 'double'.

Error in run_motor_test (line 47)
After
Undefined function 'foc_step' for input
arguments of type 'double'.

Error in run_motor_test (line 47)
R12 Dedup redundant Caused-By block ~58% reduction

Some MATLAB errors include a Caused by: section that exactly repeats the primary error message. When the Caused-By text is a substring of the main error, R12 removes the entire Caused-By block.

Before
Error using sim
Simulation stopped at time 0.035.

Caused by:
    Error using sim
    Simulation stopped at time 0.035.
After
Error using sim
Simulation stopped at time 0.035.
R13 Compact init-cond variable lists variable

Simscape and Simulink print long lists of initial condition variables when configuring a model. R13 detects the Initial conditions: block and collapses variable lists longer than 6 entries to show the first 3 and a count of the remainder.

Before

  x_rotor_speed = 0
  x_id = 0
  x_iq = 0
  x_lambda_d = 0.1230
  x_lambda_q = 0
  x_T_winding = 20
  x_T_stator = 20
  x_T_rotor = 20
After
Initial conditions:
  x_rotor_angle=0  x_rotor_speed=0  x_id=0
  [... 6 more vars ...]

Test Scenarios

The test suite in tests/ validates each rule in isolation. All tests run without a live MATLAB connection — they feed synthetic strings into the compressor and verify the output.

File Rule(s) tested What it covers
test_repeated_warnings.m R01 Verifies that 4 identical warning+trace blocks collapse to one with [×4]; checks that two different warnings are each kept; checks single occurrence is unchanged.
test_whos_table.m R03 Full 26-line whos output with 6 variables. Verifies compact one-liner format, correct size strings, class abbreviations (dbl for double, sgl for single), and that complex flag is preserved.
test_large_array.m R04 1000×1 column vector output. Verifies summary format [1000x1: first=…, last=…]; checks that small arrays (<= 20 rows) are not compressed; checks 2D array passthrough.
test_build_log.m R07 Simulink code-generation log with 10 ### lines covering 4 models. Verifies single-line summary with all model names; checks that non-build ### lines are untouched.
test_doe_progress.m R08 21 DOE point lines with consistent prefix. Verifies first 2 + elision marker + last 2; checks that 4-line sequences are not elided; checks heterogeneous lines are passed through.
test_test_runner.m R09 Full MATLAB test framework output for 8 tests (7 pass, 1 fail). Verifies PASS list, FAIL entry with diagnostic; checks all-pass case; checks all-fail case.
test_struct_display.m R10 Nested struct display (motor parameters). Verifies field inlining; checks that nested structs are not collapsed (only top-level fields); checks numeric precision preservation.
test_error_boilerplate.m R11, R12 Error with both "An error occurred" wrapper and redundant Caused-By block. Verifies wrapper stripping; verifies Caused-By deduplication; checks that non-redundant Caused-By blocks are kept.

Troubleshooting

How to confirm the proxy is active

Run a MATLAB command in Claude that would normally produce a whos table or repeated warnings. If the output contains whos: on a single line with [NxM,dbl] format, the proxy is active. If you see the full aligned table, the proxy is not in the path.

You can also check the process list:

ps aux | grep proxy.py
# Should show: python3 .../proxy.py --upstream ...

Proxy is not starting

Check Claude Desktop logs at ~/Library/Logs/Claude/ for startup errors from the proxy process.

  • Verify proxy.py is executable: ls -l proxy.py should show -rwxr-xr-x.
  • Verify Python 3: python3 --version.
  • Run the proxy manually to see errors: python3 proxy.py --upstream /Users/soorajkrishnan/matlab-mcp-server --help
  • Check that the upstream path exists: ls /Users/soorajkrishnan/matlab-mcp-server

A rule is cutting output I need

The fastest fix is to switch to --bypass mode in the config (see SWAP Guide). If you want to disable a specific rule permanently, comment out the relevant function call in compressor.py.

Rules are applied in a named pipeline — each function is clearly labeled R01–R13. To disable R04 (large array truncation), comment out the r04_truncate_arrays(text) call.

Proxy is adding latency

The proxy adds 0.065ms median overhead and 2.2ms worst-case for large responses (~51k characters). If you observe latency higher than 50ms attributable to the proxy, check for:

  • Python startup overhead (subprocess re-launch) — this should not happen after the first call.
  • Disk I/O from logging — the proxy does not write logs by default.
  • Pathological regex on malformed input — add the --bypass flag and re-test.

Claude is not seeing the full numeric result

R04 (large array truncation) shows only first and last values. If Claude needs to reason about the full array:

  • Ask MATLAB to compute a summary statistic instead: min/max/mean/std.
  • Ask MATLAB to plot the array — the plot is visible in the MATLAB desktop.
  • Store to a .mat file and ask Claude to describe the structure.
  • Use --bypass if you need to see the raw values in the Claude context.

When to disable the proxy entirely

Disable the proxy (use direct config) if:

  • You are debugging a rule that you suspect is corrupting output.
  • You need to copy-paste exact MATLAB output into a bug report.
  • You are running automated integration tests that compare exact tool output strings.

Critical Implementation Notes

⚠️ Correct config file for Claude Code

Claude Code CLI / VS Code extension reads MCP servers from ~/.claude.json → mcpServers section.
Claude Desktop app reads from ~/Library/Application Support/Claude/claude_desktop_config.json.

These are completely separate files. Editing the wrong one has zero effect.

Why matlab connects but simulink doesn't (without the fix)

The two servers use fundamentally different session modes:

ServerSession modeBehaviour
matlab --matlab-session-mode=new (default) Self-contained. Starts its own MATLAB when the first tool is called. Never fails to connect — it owns its session.
simulink --matlab-session-mode=existing Dependent. Polls for an already-running MATLAB session at startup for up to 30 seconds. If none found → permanent failure. Cannot start MATLAB itself.

The existing mode is intentional: it makes the simulink server share the same MATLAB workspace as the matlab server — same variables, same open models, same path. If simulink started its own MATLAB, model edits and workspace state would be isolated.

The problem: the matlab server starts MATLAB lazily (only when a tool is called). By the time the first matlab tool is called, the simulink server's 30-second discovery window has already expired.

The fix: --initialize-matlab-on-startup=true on the matlab server forces MATLAB to start eagerly at Claude Code launch (~15-20s). The simulink server finds the session within the 30s window and connects reliably.

Open upstream issue

This is a known gap in matlab-mcp-core-server. Issue #62 (filed Apr 2026, open): "When using --matlab-session-mode=existing, MCP server should start a MATLAB instance if it doesn't find one." Until MathWorks closes this, --initialize-matlab-on-startup=true is the correct workaround.

Startup sequence (current config)

Claude Code launches
  │
  ├─ matlab server starts
  │    └─ MATLAB boots immediately (--initialize-matlab-on-startup=true) ~15-20s
  │         └─ writes connector.securePort
  │
  └─ simulink server starts (--matlab-session-mode=existing)
       └─ polls connector.securePort every ~2s for 30s
            └─ at ~15-20s: MATLAB responds → session shared → CONNECTED ✅

⚠️ Wire format: Content-Length framing

matlab-mcp-core-server uses Content-Length framing (LSP/JSON-RPC style), not newline-delimited JSON. The proxy auto-detects this by checking for a Content-Length: header line, draining all headers, then reading exactly N bytes.

If you see raw ] characters in tool output, the proxy is passing messages through uncompressed — the Content-Length framing fix is not being applied. Verify proxy.py version with git log matlab-mcp-proxy/proxy.py.

When to revert

  • A simulation result looks wrong and you need to verify raw MATLAB output
  • An error message appears truncated and you need full context
  • The proxy crashes (exits with error) and Claude shows the server as disconnected
  • You see ] characters leaking into tool output (proxy parsing bug)
